# Business Decision Log

Status: Stage 22 accepted decisions with Stage 23 extension-boundary supplement.

## Decisions

| id | status | decision | rationale | impact |
|---|---|---|---|---|
| BDEC-001 | accepted | Use two separate business registers: `schedule` and `data_facts`. | Tasks and reported facts have different semantics and lifecycles. | Schedule model, fact model, sheet design. |
| BDEC-002 | accepted | Use `function` and `stage` as the central business coordinate of the model. | The project must support both construction work and broader delivery processes. | Schedule semantics, fact semantics, future mapping logic. |
| BDEC-003 | accepted | Treat `function` as a workstream and `stage` as a lifecycle gate within that workstream. | This provides a reusable matrix model across the entire project lifecycle. | Core business language of the project. |
| BDEC-004 | accepted | Keep `work_type` as a secondary refinement rather than the primary coordinate. | Physical work scope alone cannot represent the full investment project logic. | Construction task modeling and fact classification. |
| BDEC-005 | accepted | Keep baseline and actual views conceptually separated. | Plan and fact should remain analytically distinguishable. | Future schedule governance and reporting. |
| BDEC-006 | accepted | Represent common project processes explicitly in the schedule. | Design, approvals, procurement, control, and handover are first-class project streams. | Schedule model completeness. |
| BDEC-007 | accepted | Use confirmation before fact persistence. | The pilot needs a business trust checkpoint before writing reported data. | Fact register quality. |
| BDEC-008 | accepted | Formalize the schedule as a hybrid model rather than a flat task list. | Comparative research showed that production, delivery, and governance logic cannot be represented safely by a task-only schema. | `schedule_model.md`, `schedule_sheet.md`, future data model. |
| BDEC-009 | accepted | Use one unified `ScheduleItem` concept for activities, milestones, gates, and event-like schedule objects. | The project needs one workable pilot core that still supports approvals, payments, permits, and handover. | Schedule structure, examples, later validation. |
| BDEC-010 | accepted | Separate version from baseline designation. | Revision history and baseline status are related but different business concepts. | Versioning, schedule sheet columns, later comparison logic. |
| BDEC-011 | accepted | Separate hierarchy from coding. | Roll-up structure and reusable classification solve different business problems. | Schedule model, future analytics, sheet interpretation. |
| BDEC-012 | accepted | Treat governance records and external system links as first-class schedule context. | The project schedule must represent PMIS-like control reality without becoming a full PMIS clone. | Schedule model, mapping logic, extension design. |
| BDEC-013 | accepted | Keep facts as immutable evidence and make schedule linkage controlled rather than automatic. | Safe traceability is more important than premature automation. | Fact model, mapping logic, future bot behavior. |
| BDEC-014 | accepted | Keep heavy enterprise subsystems explicitly bounded outside the pilot core, but document them as named extension families. | Stage 23 confirmed that PMIS, EDMS, permit, smart-site, resource, and payment systems are real subsystem classes, yet absorbing them now would overengineer the pilot. | Extension architecture, integration boundaries, future promotion criteria. |
| BDEC-015 | accepted | Use one immutable `Task ID` as the single surfaced pilot identifier. | A separate surfaced lineage field adds pilot complexity without enough benefit when identifiers are never reused. | Workbook structure, dependency logic, baseline/current comparison, dashboards, bot lookup. |
| BDEC-016 | accepted | Represent the pilot control schedule as one workbook with `schedule_baseline` and `schedule_current` surfaces plus workbook metadata. | The pilot needs explicit baseline/current comparison while remaining simpler than a full schedule-version subsystem inside Sheets. | `schedule_workbook.md`, `schedule_sheet.md`, dashboard extraction. |
| BDEC-017 | accepted | Split quantity and cost into planned and actual fields, and keep in-progress timing as forecast rather than final actual. | The pilot must compare plan versus actual explicitly and avoid mixing completed duration with live projection. | Sheet schema, rules, examples, dashboard logic. |
| BDEC-018 | accepted | Use the default `T10000`-series format with step `10` for newly issued `Task ID` values. | The pilot needs a simple immutable identifier pattern that is easy to read, generate, and reserve. | `used_task_ids`, workbook logic, validation rules. |
| BDEC-019 | accepted | Use `event` as a generic row kind and move subtype detail to `Item Type`. | A generic event row keeps the pilot core simpler while preserving subtype detail where needed. | Row schema, dictionaries, examples, field rules. |
| BDEC-020 | accepted | Keep `Status Date` at the sheet/version level only. | The pilot uses one control date per schedule surface rather than per-row data dates. | `schedule_meta`, forecast rules, dashboard logic. |
| BDEC-021 | accepted | Keep `Actual` fields factual and move open-row projection into `Forecast Start`, `Forecast Finish`, and `Remaining Duration`. | Mixing facts and forecasts in the same fields would weaken control semantics and later analytics. | Field rules, row schema, examples. |
| BDEC-022 | accepted | Use controlled responsibility buckets for `Responsible`. | The pilot needs stable ownership labels for grouping and control rather than person-specific names. | Dictionaries, validation, dashboards, bot lookup. |
| BDEC-023 | accepted | Assemble the first baseline as one full reference-template project `P01` and clone it later into `P02-P07`. | One complete project template is easier to validate, govern, and reuse than inventing multiple partially specified projects at once. | Baseline assembly order, workbook population, future cloning logic. |
| BDEC-024 | accepted | Use a normalized `P01` row-count model that preserves the approved early-phase detail and the overall 135-row pilot target. | Earlier planning discussions contained conflicting subtotal counts; a single normalized implementation model is needed for docs, sheets, and QA. | `schedule_baseline`, template documentation, test checks. |
| BDEC-025 | accepted | Keep the richer 152-row `P01` variant when the additional rows add useful delivery, trade, and commissioning detail. | The pilot benefits from preserving meaningful variations instead of trimming them only to satisfy a compactness target. | `schedule_baseline`, `used_task_ids`, template documentation, later cloning logic. |
| BDEC-026 | accepted | Allow `schedule_baseline` to store planned progress state as of the sheet `Status Date` for actionable non-`wbs` rows. | The pilot baseline must support planned-as-of-date analytics without populating actual fields. | Baseline enrichment logic, examples, dashboards. |
| BDEC-027 | accepted | Derive baseline `Status` from `Percent Complete` and keep `wbs` rows blank for `%`, `Status`, and `Planned Cost`. | This keeps baseline semantics simple and avoids premature WBS roll-up logic in the pilot. | Field rules, template defaults, validation expectations. |
| BDEC-028 | accepted | Use `Global USD 2026` and a `hybrid split` planned-cost model with a normative cost reference catalog. | The pilot needs portable planned-cost assignment without country-locking, while avoiding double counting between procurement and execution rows. | `planned_cost_reference.md`, schedule enrichment, later dashboard interpretation. |
| BDEC-029 | accepted | Exempt `schedule_baseline` from validation rules that require `Actual Start` and `Actual Finish` on `done` rows. | Baseline `done` is a planned-as-of-date state, not factual completion, so forcing `Actual*` fields would break the accepted pilot semantics. | Workbook validation logic, field rules, pilot QA behavior. |
| BDEC-030 | accepted | Implement `Status Date` as `=TODAY()` on both `schedule_baseline` and `schedule_current`. | The pilot should always read planned/current state against the live control date without manual date maintenance. | `schedule_meta`, baseline statusing, dashboard interpretation. |
| BDEC-031 | accepted | Add a manual dictionary-backed `Phase` field to both schedule sheets between `Work Type` and `WBS Path`. | The portfolio baseline needs an explicit 7-phase coordinate for easier filtering and reporting, while keeping `Stage` focused on lifecycle semantics inside a function. | Sheet schema, dictionaries, validation, examples, dashboards. |
| BDEC-032 | accepted | Seed portfolio projects with project-banded `Task ID` ranges `T1xxxx` to `T7xxxx`. | Project-specific ID bands make multi-project control sheets easier to read and govern than one long global sequence. | `used_task_ids`, clone logic, schedule readability. |
| BDEC-033 | accepted | Scale the baseline to `P01-P07` so that all 7 macro phases are represented on the live April 2026 control date. | The pilot needs one portfolio surface that covers the full lifecycle spectrum without restructuring the model during fact input and dashboard work. | `schedule_baseline`, cloning logic, portfolio analytics. |
| BDEC-034 | accepted | Apply a one-time manual historical backfill to `schedule_current` as of `2026-04-08`, closing past-due non-`wbs` rows with `Actual = Planned`. | The pilot needs a usable current surface immediately, without introducing date-driven actual formulas or a heavier automation layer. | `schedule_current`, field rules, validation behavior. |
| BDEC-035 | accepted | Feed `Actual Quantity` for open quantity-driven rows in `schedule_current` directly from `data_facts` by `Stage + Function + Work Type + Unit`. | This is the simplest robust pilot bridge between facts and schedule progress while postponing stronger row-level matching logic. | `schedule_current`, fact-to-schedule mapping, pilot limitations. |
| BDEC-036 | accepted | Accept duplicate quantity aggregation across multiple `schedule_current` rows that share the same `Stage + Function + Work Type + Unit` coordinate. | Avoiding this duplication now would require more enterprise-style matching and identity logic than the pilot justifies. | `schedule_current`, mapping limitations, post-pilot hardening scope. |
| BDEC-037 | accepted | Calculate quantity-driven `Actual Cost` in `schedule_current` with the proportional pilot formula `ROUND(Actual Quantity / Planned Quantity * Planned Cost, 2)`. | The pilot needs a transparent cost-to-progress proxy before true commercial actuals are integrated. | `schedule_current`, field rules, dashboard interpretation. |
| BDEC-038 | accepted | Keep open-row `Actual Start`, `Actual Finish`, and non-quantity `Percent Complete` bot-maintained rather than formula-driven in the pilot. | These fields require interpretation and evidence assessment; a simple formula would create low-trust noise. | Bot workflow, current-sheet governance, post-pilot automation scope. |
