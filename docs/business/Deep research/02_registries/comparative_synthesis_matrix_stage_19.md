# Comparative Synthesis Matrix: Stage 19

This matrix is the first deep-pass comparative synthesis across all currently researched layers and zones:

- universal and institute layer
- regional layer
- academic formalization layer
- enterprise practice layer
- software-native layer

It is intentionally synthetic. It does not replace the source-level registries. It integrates them.

## Matrix B. Universality, Regionality, and Layer Specificity

| Row ID | Synthesis class | Main objects / practices | Strongest evidence zones or layers | Interpretation | Modeling implication |
| --- | --- | --- | --- | --- | --- |
| `UNI-001` | Universal across nearly all layers | activity/task, milestone, dependency, calendar, baseline, WBS, actuals, progress control | universal core, USA, software layer | These are the durable backbone of schedule systems | Must exist in any serious target model. |
| `UNI-002` | Frequent but not universal | resource groups, work packages, control accounts, phase/stage fields, narrative reporting | USA, Middle East, software layer, institutes | Strong recurring second-order structures | Likely core candidates, but not every grammar uses them identically. |
| `REG-001` | Region-strong production objects | `POS`, `PPR`, organization design, cyclograms, smart-site control | CIS, China | Production planning is not represented identically across regions | Target model should allow regional extensions rather than force one production grammar. |
| `REG-002` | Region-strong delivery-governance objects | project cycle stage, PPP gate, handover strategy, readiness plan, PMIS control cycles | EU, Middle East, USA owner layer | Delivery schedules carry many non-physical control objects | Delivery-model support must be explicit, not treated as optional metadata. |
| `LAY-001` | Academic-strong objects | network methods, resource leveling, earned value foundations, planning documents | academic layer | Academia still shapes baseline schedule grammar | Keep teaching-origin constructs visible when interpreting regional data. |
| `LAY-002` | Enterprise-strong objects | PMIS, project master schedule, KPI cycle, integrated controls review, payment/change linkage | enterprise layer | These are central in live project systems but often underrepresented in textbooks | Enterprise operating objects should be first-class in the business model. |
| `LAY-003` | Software-strong objects | configured fields, schedule sheets, version history, audit records, linked objects, smart-site platforms | software layer | Software expands the schedule into a hybrid data environment | The model must support configurable and linked object structures. |
| `DIG-001` | Emerging digital-governance objects | digital archive key, smart cockpit, item reference, digital work package, PMIS system-of-record reference | China, CIS enterprise, Middle East, software layer | Digital-governance is now substantive, not peripheral | The target model should not isolate schedule from digital-control context. |

## Matrix C. Academic vs Enterprise vs Software Divergence

| Row ID | Comparison theme | Academic layer | Enterprise layer | Software-native layer | Comparative synthesis |
| --- | --- | --- | --- | --- | --- |
| `DIV-001` | What is "the schedule"? | Usually a planning and control artifact defined by methods | A governed operating artifact inside PMO/PMIS routines | A hybrid data structure with objects, versions, links, and schemas | The target model must reconcile all three, not pick only one definition. |
| `DIV-002` | Core object emphasis | Tasks, networks, resources, and sometimes planning documents | Master schedules, PMIS records, controls packages, handover objects, dashboards | Tasks plus sheets, configured fields, versions, logs, linked records | Enterprise and software layers materially widen the object model. |
| `DIV-003` | Reporting and change | Often taught as managerial process or assignment | Recurring governance cycle with escalation, KPI review, payment and change implications | Embedded in notes, logs, version summaries, audit trails, issue links | Report/log should be modeled as both process and data. |
| `DIV-004` | Completion and handover | Often underemphasized or treated late | Explicit readiness, transition, testing, commissioning, and handover governance | May appear as phase fields, version objects, linked completion records | Closeout and readiness need stronger first-class support. |
| `DIV-005` | Digital context | Often limited to tools or introductory BIM/intelligent-construction concepts | PMIS, BIM, digital cockpit, EDMS, smart-site control | Linked objects, digital keys, integration boundaries, platform state | Digital-governance should be modeled as structural, not auxiliary. |

## Matrix E. Composite Implications for Target Modeling

| Row ID | Comparative conclusion | Why it matters |
| --- | --- | --- |
| `IMP-001` | No single region or layer is sufficient as the source-of-truth model. | Every zone is strongest in a different part of the schedule universe. |
| `IMP-002` | USA and Middle East are strongest for explicit enterprise controls and owner governance. | They are the best anchors for rules, governance, and PMIS-linked schedule obligations. |
| `IMP-003` | CIS and China are strongest for document-system and production-organization logic. | They help prevent the model from collapsing into a task-only enterprise CPM schema. |
| `IMP-004` | EU is strongest for phase-gate, programme, procurement, and handover governance. | It is essential for full project-delivery modeling. |
| `IMP-005` | Software confirms that the live schedule system is hybrid. | The target model must support tasks, documents, versions, logs, codes, links, and digital-governance objects together. |
| `IMP-006` | Academic, enterprise, and software layers must remain separable in analysis but integrated in modeling. | Mixing them too early causes category errors and weak target architecture. |
